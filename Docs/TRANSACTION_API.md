# V1 Milestones 2 and 3

The separate Fastify backend owns persistence, validation, and calculations. Next.js remains the foundation placeholder. This milestone adds no expense UI, recurring rule API/generator, dashboard, authentication, or later-version features.

## Database design

The source schema is `apps/api/prisma/schema.prisma`. Two migrations create the schema and add PostgreSQL CHECK constraints, which Prisma cannot represent directly. Apply migrations with `npm.cmd run db:migrate`; do not substitute `db push`, which would omit custom constraints.

| Table | Contents and relationships |
| --- | --- |
| `categories` | UUID, unique name, creation/update timestamps. Seeded with all 16 PRD defaults. |
| `transactions` | Expense type/nature, total/my share/recoverable, currency, description, merchant, category ID, subcategory, notes, local date/time/timezone, payment method, split fields, optional recurring rule and occurrence identity, audit timestamps. |
| `recurring_expenses` | Name, category, total/my share/currency, split fields, frequency, start/end/next due dates, timezone, active flag, notes, audit timestamps. Schema only. |

UUIDs are generated by Prisma. Category foreign keys and transaction-to-recurring-rule foreign keys use restrictive deletion. Removing a rule or category cannot silently erase history. Editing a rule does not rewrite stored transactions.

The database enforces positive total amounts, share bounds, exact recoverable balance, equal-split arithmetic, consistent split metadata, nonblank names/descriptions, currency format, and valid recurring date ranges. `recurring_expense_id + occurrence_date` is unique for generated records. Occurrence identity is separate from the editable transaction date. Unsplit transactions have null participant count and split type. Weekly/monthly/yearly frequencies are the only schema values.

History has an index on descending transaction date, time, and ID. Category references and active recurring due dates are also indexed. Dates use PostgreSQL `DATE`, wall-clock times use `TIME(0)`, and audit fields use `TIMESTAMPTZ(3)`. Prisma maintains `updated_at` on writes; direct SQL maintenance must update that field explicitly.

The category seed is repeatable: existing IDs and data are retained. It inserts missing defaults without deleting or reseeding transactions. Optional subcategory text is available on transactions; category editing and a subcategory catalogue are not implemented.

## Money and date decisions

- Money is PostgreSQL `DECIMAL(14,2)`. JSON amounts are decimal strings, e.g. `"500.00"`. JSON numbers, exponent notation, zero/negative expenses, more than two decimal places, and amounts over `999999999999.99` are rejected.
- Calculations use Prisma's decimal arithmetic. Equal splits round the user's share to two decimal places using half-up rounding; recoverable is the total minus that rounded share. `1000 / 3` gives `333.33` and `666.67`. A `0.01` expense split two ways gives a user share of `0.01` and recoverable `0.00`. No per-person remainder allocation is implemented.
- V1 API supports INR only. The database retains a currency code, and currency handling is kept separate from calculations so other currency rules can be added later.
- Clients cannot submit `my_share`, `recoverable_amount`, IDs, audit fields, expense nature/type, or recurring occurrence fields. Unknown fields are rejected, including on PATCH.
- Missing transaction date/time use the request's `time_zone`, or `APP_TIMEZONE`, or the host's detected local timezone, in that order. Use an IANA timezone such as `Asia/Kolkata`; fixed offset strings are rejected. `APP_TIMEZONE` is validated at startup.
- Date/time represent local calendar values, separate from entry timestamps. Past entries preserve those values exactly. Explicit times are not converted into UTC instants, so daylight-saving gaps/folds are not resolved. Changing only the timezone on PATCH retains the stored wall-clock date/time.
- PATCH preserves omitted fields, recalculates money, and clears split metadata when switching to `is_split: false`. A row lock protects concurrent partial edits. Explicit `null` clears merchant, notes, subcategory, or payment method; it is not accepted for required fields or date/time.
- Delete is a hard delete and requires `?confirm=true`. The future expense UI must obtain confirmation before sending it.

## REST endpoints

Base URL: `http://localhost:3001`.

| Method | Path | Result |
| --- | --- | --- |
| GET | `/health` | 200, `{ "status": "ok" }`; process liveness only |
| GET | `/categories` | 200, `{ "data": [{ "id": "...", "name": "..." }] }` |
| POST | `/transactions` | 201, saved transaction; `Location` header points to its detail URL |
| GET | `/transactions?limit=50&offset=0` | 200, `{ "data": [...], "limit": 50, "offset": 0 }` |
| GET | `/transactions/:id` | 200, one transaction |
| PATCH | `/transactions/:id` | 200, updated transaction |
| DELETE | `/transactions/:id?confirm=true` | 204, empty body |

Lists sort by transaction date descending, time descending, then UUID descending for deterministic ties. Limit is 1–100; offset is nonnegative. Pagination does not return a total count. No filtering or analytics endpoints are included.

Create requires `total_amount`, `description`, and `category_id`. Optional fields: `currency`, `merchant`, `subcategory`, `notes`, `transaction_date` (`YYYY-MM-DD`), `transaction_time` (`HH:mm` or `HH:mm:ss`), `time_zone`, `is_split`, `participant_count`, `split_type`, and `payment_method`. A split requires an integer participant count of at least 2, including the user; its type defaults to `equal`. Payment method values are `UPI`, `CreditCard`, `DebitCard`, `Cash`, `BankTransfer`, `Wallet`, and `Other`.

PATCH accepts any nonempty subset of the same editable fields. When enabling a split, include participant count unless the transaction is already split. To disable splitting, send `{ "is_split": false }`.

Response amounts always have two decimal places. Date/time are returned as `YYYY-MM-DD` and `HH:mm:ss`; audit timestamps are ISO UTC strings. Responses include `category_id`; category names are available through `/categories`.

Invalid input, nonexistent categories, and unconfirmed deletion return 400. Missing transactions return 404; duplicate unique records return 409. Unexpected failures return 500 with a generic message. Validation responses list field names and messages. Raw database errors, credentials, and financial payloads are not returned or logged.

## Local setup and manual API check

From the project root, after configuring the environment files described in the README:

```powershell
npm.cmd ci
docker compose up -d --wait db
npm.cmd run db:generate
npm.cmd run db:migrate
npm.cmd run db:seed
npm.cmd run db:check
npm.cmd run dev:api
```

An existing PostgreSQL server can replace Docker; set `DATABASE_URL` in `apps/api/.env` accordingly. The portable database used by tests is isolated and is not the application's development database.

In a second PowerShell terminal:

```powershell
$api = 'http://localhost:3001'
$categories = Invoke-RestMethod "$api/categories"
$categoryId = ($categories.data | Where-Object name -eq 'Food & Dining').id
$payload = @{
  total_amount = '1000.00'
  description = 'Dinner'
  category_id = $categoryId
  is_split = $true
  participant_count = 3
  transaction_date = '2026-09-05'
  transaction_time = '20:30'
  time_zone = 'Asia/Kolkata'
} | ConvertTo-Json
$expense = Invoke-RestMethod "$api/transactions" -Method Post -ContentType 'application/json' -Body $payload
$expense
Invoke-RestMethod "$api/transactions/$($expense.id)"
Invoke-RestMethod "$api/transactions?limit=10&offset=0"
$edit = @{ total_amount = '1200.00'; participant_count = 4 } | ConvertTo-Json
Invoke-RestMethod "$api/transactions/$($expense.id)" -Method Patch -ContentType 'application/json' -Body $edit
Invoke-RestMethod "$api/transactions/$($expense.id)?confirm=true" -Method Delete
```

Expected: initial share `333.33`, recoverable `666.67`, date September 5; after editing, share `300.00` and recoverable `900.00`; after deletion, detail returns 404. Sending a numeric amount, negative amount, impossible date, calculated share, or unknown category must return 400. Repeating the seed must leave exactly 16 defaults with stable IDs.

## Automated verification

```powershell
npm.cmd test
npm.cmd run test:integration
npm.cmd run typecheck
npm.cmd run lint
npm.cmd run build
npm.cmd run db:validate
```

Unit tests cover validation, financial rounding/bounds, timezone boundaries, and explicit past values. Integration tests start real PostgreSQL 17, apply migrations twice, seed repeatedly, inspect schema constraints, and exercise the actual Fastify routes with Prisma. They include persistence through a second API instance, update concurrency, invalid requests, database invariants, recurrence occurrence uniqueness, historical independence, and sanitized failures. Tests of recurring rows only verify Milestone 2 schema behavior; no recurring generator is present.

Integration tests download portable PostgreSQL binaries through npm, use a fresh local cluster under ignored `.test-postgres/run-*`, bind loopback on a temporary port, and remove that cluster after shutdown. They do not use or alter the application's `DATABASE_URL`. Run them as a regular OS user; PostgreSQL cannot run as Unix root. A crash may leave a test directory, which can be removed after its PostgreSQL process has stopped.

Verified on this Windows workspace: 10 unit/foundation tests and 13 PostgreSQL integration scenarios passed (the integration runner reports 14 including its parent test). Both workspace type checks, lint checks, production builds, and Prisma schema validation passed. Compiled backend HTTP startup passed on port 3101 because port 3001 was already occupied. The smoke-test server and disposable database were stopped and the test cluster removed. No permanent development database was installed or migrated. Runtime dependency audit is clean; the pre-existing three development-tooling advisory entries remain documented in the README.
