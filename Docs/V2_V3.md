# V2 natural-language entry and V3 analytics

V1 remains intact. This change adds natural-language expense drafts and expanded analytics. It does not add people/settlement ledgers, budgets, financial accounts, income, imports/exports, automated ingestion, or V4+ features.

## Architecture

The Next.js/React frontend in `apps/web` still communicates over REST with Fastify/Node.js/TypeScript in `apps/api`. PostgreSQL and Prisma remain the source of truth. There are no Next.js API routes or Server Actions handling backend logic.

Natural-language flow:

1. User enters a message on Transactions and selects Review expense. Dashboard retains its manual Add Expense action.
2. `POST /expense-parser/parse` reads the existing categories and calls an injected `ExpenseProvider`.
3. The Groq implementation sends only the expense message, category names, and extraction instructions. It never sends transaction history, database credentials, or the API key as model context. The key is used only in the HTTP Authorization header.
4. Strict Zod validation checks the extraction. Backend code resolves supported date/time expressions and validates category mapping. Monetary previews use the existing `calculateAmounts` function.
5. The response is an in-memory draft; no draft table or transaction is written.
6. The frontend opens the shared expense form, with all fields editable. Confirm expense calls the existing `POST /transactions` endpoint and transaction service. Final financial values are calculated again there. Cancel does not save anything.

Provider abstraction: `ExpenseProvider.extract(text, categories): Promise<unknown>`. The service owns validation and normalization regardless of provider. Tests inject a mock provider; no production environment flag enables fake AI results.

## Groq model and configuration

Default provider: **Groq**, using the native Node fetch client and its OpenAI-compatible chat-completions REST endpoint. Default model: **`qwen/qwen3.8-27b`**. No SDK or chart-library dependency was added.

The current [Groq model list](https://console.groq.com/docs/models) lists this Qwen model, and [Groq structured-output documentation](https://console.groq.com/docs/structured-outputs) lists strict JSON-schema support. It was chosen for Qwen compatibility and stronger schema adherence for extraction. It is a preview model and is not the cheapest Groq model; availability may change. `GROQ_MODEL` permits deliberate model replacement without changes to transaction logic. A replacement must support strict structured output; `openai/gpt-oss-20b` is a documented Groq-hosted alternative, but is **not selected automatically**. Providers are never silently substituted.

In **`apps/api/.env` only**:

```dotenv
GROQ_API_KEY=your_key_here
GROQ_MODEL=qwen/qwen3.8-27b
```

Leave the key blank to run everything except live AI extraction. Manual entry and analytics still work. Never put this key in `apps/web`, `NEXT_PUBLIC_*`, or source control. Restart the backend after changing these values. Example settings are in `apps/api/.env.example`.

The normal automated tests never depend on Groq or an API key. After configuring the key, `npm.cmd run test:groq:live` checks the authenticated models list and parses five fixed samples: merchant/category, yesterday/equal split, missing amount, named date, and explicit time. It checks the normalized drafts and exact split preview, and performs no database writes. These are separate, potentially billable provider calls.

## Draft validation and ambiguity

The model supplies nullable amount, numeric evidence (`amount_source`), description, merchant, category/confidence, raw date/time expressions, split intent/count, and notes. It cannot supply authoritative shares or category IDs. Unexpected fields or an invalid schema are rejected.

- Amount must be valid under existing exact-money rules and match numeric evidence actually present in the message. Missing/unsupported amounts stay blank. No amount is inferred from a merchant/category.
- Description, merchant, notes, and date/time expression text must be grounded in the original message. Ungrounded description/date/time fields require correction; ungrounded optional merchant/notes are omitted. This conservative check can require manual correction when the model paraphrases rather than extracts.
- Categories map case-insensitively to existing records. Confidence below 0.6 or an unknown name falls back to Other, with a warning; if Other is unavailable the category is left unselected. Confidence is model-reported, not a calibrated probability.
- Today and yesterday use the server clock in the requested timezone. Last Friday means the most recent strictly earlier Friday, including seven days ago if today is Friday.
- ISO dates, English named-month dates (`Sep 3`, `3 September`, optionally a year), and common 12/24-hour times are resolved deterministically. A missing year uses the current local year with a warning. Unknown dates/times stay blank. If absent entirely, local current date/time is used.
- V2 supports one INR expense per message and equal splits only. Ambiguous participant count remains blank, and users must supply the total count including themselves. The AI interprets intent; the review step remains mandatory because semantic errors are still possible.
- Preview amounts are backend-calculated and returned when possible. The review form asks users to save to see their final shares, avoiding stale previews after editing.
- Provider errors, rate limits, timeout, malformed JSON, and invalid output return safe errors. Original text remains available, with an Enter manually action. The provider call has an 8-second timeout, bounded input, and output-token limit. Raw provider error bodies are not returned or logged.

## REST endpoints

| Endpoint | Contract |
| --- | --- |
| `POST /expense-parser/parse` | `{text, time_zone?}`; returns `{draft, category_name, warnings, confidence, preview}`; never saves expenses; records provider usage metadata |
| `POST /transactions` | Existing confirmation/create endpoint; unchanged authoritative transaction service |
| `GET /analytics/monthly?month=2026-09&time_zone=Asia%2FKolkata` | Defaults to current local month; totals, all-category percentages, zero-filled daily series, previous-month comparison |
| `GET /analytics/range?start_date=2026-09-01&end_date=2026-09-07&time_zone=Asia%2FKolkata` | Inclusive custom range, maximum 366 days; same summaries and comparison with the immediately preceding equal-length range |
| `GET /dashboard` | V1 contract preserved for existing consumers, including variable-only category breakdown |

Parser input is limited to 1,500 characters and an 8KB HTTP body. Missing provider configuration/unavailability returns 503, invalid extraction 502, rate limit 429, invalid requests 400. A partial draft containing missing fields is a successful parse response; the normal form/API still reject incomplete saves.

The original V2/V3 implementation did not need schema changes. The subsequent requested Groq usage tracking adds the `GroqApiUsage` model (`groq_api_usage` table) through migration `20260910000000_groq_api_usage`. Existing transaction tables and financial calculations are unchanged. The existing merchant column is exposed in the shared form and retained when editing transactions. Existing transaction-date indexes support analytics queries.

## Groq usage in Prisma Studio

Run `npm.cmd run db:migrate`, restart the backend, and start or restart `npm.cmd run db:studio`. At **http://localhost:5555**, open **GroqApiUsage** alongside Category, Transaction, and RecurringExpense. Sort `created_at` descending to see the latest calls; filter by model, date, or outcome as needed.

Each production app parser call records configured model, timestamp, HTTP status, prompt/completion/total tokens reported by Groq, duration in milliseconds, and provider outcome. `response_received` means a schema-valid provider response, not a saved transaction. `invalid_response`, `http_error`, and `request_failed` distinguish unsuccessful attempts. Missing token counts are null (unknown), never an invented zero. No expense text, model output, or API key is stored. Missing-key failures make no provider request and create no usage row. Logging failures emit a safe backend warning and do not fail parsing.

Tracking starts after this migration and backend restart. It covers calls made through this app, not past calls or other apps using the same key. The standalone `test:groq:live` command deliberately remains database-free and is not included. Local logs are best-effort, not a billing ledger: process/network failures can prevent complete accounting. Use Groq's account usage console for billing and account-wide history. Prisma Studio displays these records as a table; it does not add custom charts or billing totals. Groq's [completion response usage fields](https://console.groq.com/docs/api-reference) provide the token counts.

Usage-tracking verification: 20 backend unit tests, 24 PostgreSQL integration tests, and 8 browser acceptance scenarios passed, along with both applications' type-check, lint, and production builds. Prisma schema validation passed and the additive migration was applied to the local database. Tests cover token recording, failed/malformed responses, unknown counts, missing keys, recorder failures, production recorder persistence without expense creation, and quick entry remaining only on Transactions.

## Analytics definitions and dates

- Personal spending: sum of `my_share` across variable and generated recurring transactions.
- Variable/recurring spending: `my_share` separated by `expense_nature`.
- Total paid: sum of `total_amount`; recoverable: sum of `recoverable_amount`.
- Category totals: all personal spending, including recurring, sorted descending. Percentage denominator is overall personal spending. Zero totals produce zero percentages; two-decimal percentages can sum to 99.99 or 100.01 due to rounding.
- Daily series: sum of personal spending for every transaction date in the selected period, with zero entries for dates without transactions.
- Daily variable average: variable spending divided by elapsed calendar days within the selected period, including today. Completed periods use all days; wholly future periods return null. All recorded transactions in the period, including future-dated entries, contribute to its totals.
- Monthly comparison uses the previous complete calendar month. The UI explicitly notes when the selected period is incomplete. Percentage change is null if previous spending is zero; absolute change remains available. Range comparisons use an immediately preceding equal-length period, not necessarily a calendar-aligned year/week.
- Actual transaction dates determine inclusion, never `created_at`. Timezone determines local today and default/current periods, not conversion of stored transaction dates.

PostgreSQL groups by date, category, and expense nature; the backend combines those aggregates using decimal arithmetic in a repeatable-read snapshot. It does not load all raw transactions into React. Money remains decimal strings. The SVG chart converts amounts to numbers only for display coordinates; exact values remain available in the accessible daily-values table.

## Verification commands and manual checklist

Run commands sequentially to avoid concurrent Prisma generation:

```powershell
npm.cmd test
```

Manual acceptance:

1. With Groq configured, review `450 dinner at Meghana`; check amount/merchant/category/date, cancel and verify nothing was saved, then parse and confirm.
2. Review `1200 dinner yesterday split 4`; verify yesterday and four people. Confirm and check 300 share / 900 recoverable. Edit count before confirmation to verify final shares use the updated input.
3. Review `coffee at Starbucks`; amount must remain blank. Supply the amount or cancel.
4. With no key or provider unavailable, verify useful error, retained input, and manual entry still works.
5. In an otherwise empty month, create variable personal spending of 3,000 and generated recurring personal spending of 14,000. Verify overall 17,000, correct paid/recoverable values, and category/daily sums reconcile.
6. Inspect an empty month, a split-only month, and a month without previous data; there must be no NaN or divide-by-zero percentage.
7. Enter a historical expense; verify its date's chart value and month/category totals. Check range presets and exact daily values on mobile.

## Scope and limitations

Reverification on 2026-09-10: 19 backend unit tests, 23 integration tests (including enclosing tests), 9 frontend tests, and all 8 Chromium acceptance scenarios passed. Both apps passed type-check, lint, and production builds. The configured Groq account/model passed all five live extraction checks after allowing network access; the first sandboxed attempt could not connect. No live check wrote transactions. Automated browser parsing still uses the test-only injected provider so routine tests remain independent of Groq. Mobile review and analytics screenshots were inspected; screenshots are in `Docs/verification/v2-review-mobile.png`, `v3-analytics-desktop.png`, and `v3-analytics-mobile.png`.

The detailed V2/V3 implementation request is covered. The broader PRD's illustrative trend ideas (merchant totals, weekend-versus-weekday comparisons, and fastest-growing categories) are not separate implemented reports; V3 currently provides overall period comparison, category totals/percentages, and daily series. Category learning remains a future enhancement, and split previews are returned by the backend but final shares are displayed after confirmation in the UI. Supported custom ranges are limited to 366 days. These boundaries are explicit rather than unfinished background work.

During this audit, the sandboxed Playwright runner stalled while stopping its Next.js test server after all assertions passed. Stopping only the three test-server processes identified in that run allowed Playwright to finish with exit code 0 (`8 passed`). The isolated PostgreSQL directories had already been cleaned up. The persistent development database was not modified by these tests.

This remains a local single-user app. There is no automatic category-learning system, background AI processing, general assistant, settlement tracking, multi-currency entry, or V4 functionality. Changing the model requires a compatible Groq configuration and live testing; model catalog availability alone does not prove access for a particular account. Parsed drafts are not persisted, and refreshing/navigating away clears unsaved input. Browser testing covers Chromium desktop/mobile viewports, not every physical browser/device.
